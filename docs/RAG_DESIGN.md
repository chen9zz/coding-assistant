# Demo 规模的仓库 RAG 设计

状态：**仅设计，尚未实现或测量**。现有能力是 Tree-sitter 仓库映射、ripgrep 搜索及分页读取，不能称为向量 RAG。

## 推荐第一版

使用 Python 标准库 `sqlite3` + SQLite FTS5/BM25，复用已有 Tree-sitter，为单个授权仓库提供带来源的全文检索增强生成。不新增向量数据库、不新增付费 embedding API，不改变 MySQL 任务/事件存储，也不替换现有搜索工具。

```text
操作者指定仓库 → 有界文件筛选 → 代码/Markdown 分块
                                 ↓
                       本地可重建 FTS5 索引
                                 ↓
Agent → rag_search → 排名片段 + 路径/行号/内容摘要
                                 ↓
                    读取并核对当前文件 → 推理/补丁/原验收
```

FTS5 提供全文匹配及 `bm25()` 排序；默认分词对无空格中文不充分。Demo 可对文档使用 trigram 分词并保留短查询的 ripgrep 回退，部署前检查 SQLite 的 FTS5/trigram 可用性。不要把词法匹配称为语义检索。[SQLite 官方说明](https://www.sqlite.org/fts5.html)

## 数据与接口

- 首期范围：Python 代码和 Markdown 文档。代码优先按函数/类切分，超长块再按行切；文档按标题切。建议单块 100–200 行、可配置小幅重叠，实际以评估调整。
- 索引字段：仓库身份、基准提交、文件相对路径、起止行、符号/标题、文本、完整源文件 SHA-256、分块器版本。正文及元数据与 FTS 表分开保存，便于更新和溯源。
- 建议默认上限：500 个文件、10 MB 原始文本、单文件 256 KB；超限明确报告。仅包含授权目录内允许的普通文本文件，排除链接、二进制、Git 元数据、忽略文件、依赖、数据库、运行日志、密钥与本地配置。遵守既有敏感路径策略，不能只靠文件后缀判断安全。
- 索引由操作者显式建立，保存在仓库外私有目录，可随时重建；模型不能指定任意索引源路径。无需向网络发送原文或 embedding。
- `rag_search(query, top_k=5)`：只读、有参数长度和时限限制；最多返回 5 块、总计 8000 字符，包含路径、行号、源文件摘要与排序分数。绑定当前任务仓库身份；查询使用参数绑定和受限查询语法。
- 搜索后核对当前 worktree 的源文件摘要。命中旧版本则丢弃/重新索引，不把旧行号当成当前事实。补丁成功后使涉及文件失效；删除文件必须移除旧条目。第一版串行更新即可。

## 与 Skills、Agent Loop 的关系

`rag_search` 是 Agent Loop 的另一个只读工具；命中结果作为不可信证据进入上下文，不能覆盖系统策略、注入工具许可或触发执行。模型可据来源继续调用现有读取工具，修改仍走原网关与验收。

首期只索引代码和项目文档。Skills 继续由 `skill_list` / `skill_read` 显式加载，避免检索结果被误当成已经授权的技能指令。以后若检索技能，应只检索元数据，选中后再显式读取；写入仍逐次审批，与索引更新解耦。

## 验收而非堆技术栈

先准备 20–30 个有标准证据位置的小问题：函数定位、跨文件调用、错误定位、文档约束和中文问题。用现有 ripgrep/仓库映射作基线，比较 Recall@5、MRR、引文正确率、检索延迟、索引大小、上下文字符数；再以相同模型和固定任务预算对比修复通过率与成本。所有指标是拟测量项，当前没有成绩。

安全用例必须包括越界/链接/敏感文件排除、恶意文档指令不执行、跨仓库隔离、修改/删除后的旧片段失效、超限输入及缺失 FTS5 时明确失败或显式回退。若词法方案对语义问题确实不足，再增加本地 embedding 与小规模混合排序，另行验证模型许可证、资源占用和收益；当前不选向量库或宣称已实现混合 RAG。
