## 二、本机模型与 MySQL 接入

### D01：MySQL 在受限环境中的启动探测崩溃

- 现象：已有 mysqld 的帮助探测在受限环境报 Aligned_atomic 初始化异常。
- 排查：相同命令在获准的本机环境成功，先区分执行环境限制与 MySQL 本身损坏。
- 处理：不重装、不覆盖原数据库；新建 forgepilot-local/mysql-data 隔离实例，127.0.0.1:13306，禁用 mysqlx。
- 安全：独立应用账号只允许 forgepilot_live/forgepilot_test 的必要权限；密码文件 0600，目录 0700；管理凭据与应用凭据分开。
- 证据：真实 MySQL 集成 11 passed、1 SQLite 专属 skip；当时全量 302 passed、1 skip。未验证公网数据库或远程 TLS。

### D02：模型密钥安全输入与环境差异

- 密钥由用户在启动脚本隐藏输入，未写入代码、聊天、命令行参数或配置文件。
- 启动脚本检查数据库与验收哈希后启动工作台，不自动提交付费任务。
- 曾使用未安装的 httpx 编写检查脚本，改用标准库 urllib；这是操作脚本问题，不是 DeepSeek API 故障。
- UI 父进程持有密钥，新 worker 继承指定凭据；测试子进程不继承模型/数据库密钥。

## 三、真实模型运行暴露的问题

### D03：tree-sitter 原生崩溃

- 现象：首轮在 INDEXING 阶段 SIGBUS/SIGSEGV，尚未完成模型工具循环。
- 复现：独立大仓库扫描与 2000 函数遍历子进程触发 tree-sitter 0.26.0 崩溃；检查 macOS 崩溃栈，不读取进程秘密。
- 修复：项目依赖锁到 >=0.25.2,<0.26；只更新项目虚拟环境。
- 验证：相同仓库扫描连续三次成功，大遍历回归通过。不能把此机器复现扩展为所有平台/版本都存在该缺陷。

### D04：仓库摘要预算遗漏 imports/test_files

- 现象：绕过解析器崩溃后，真实仓库仍无法满足 12k 字符地图预算。
- 原因：缩减 symbols/files/snippets，却未缩减 imports/test_files；删除其他内容也不能达标。
- 修复：把全部可变元数据计入裁剪，保持文件关联一致；不单纯放大预算。
- 验证：80 个测试文件、大量 import 的 2000 字符上限回归先失败后通过；真实仓库地图约 11658 字符。

### D05：原生模型响应包含多个工具调用

- 现象：DeepSeek 已成功鉴权并执行 repo_map，下一步报 invalid decision。
- 排查：增加固定枚举诊断 multiple_tool_calls/incomplete_decision/unknown_tool/missing_final_text，禁止输出原始响应。
- 原因：即使请求 parallel_tool_calls=False，实际回复仍可能包含多个调用。
- 修复：OpenAI-compatible 协议只采纳首个提议；其余丢弃，不排队，不假装执行；下一次用真实执行结果重新规划。Anthropic 路径仍保持原校验。
- 验证：真实本地 HTTP 协议回归，包括首调用 DENIED、第二危险调用不会执行；48 项 provider 测试通过。

### D06：用户终端找不到 rg

- 现象：Codex 环境里存在 bundled rg，但用户启动的 worker 环境没有。
- 修复：本机 Homebrew 安装 ripgrep 15.2.0 与 pcre2；短期逐项审核仓库内 grep/sed 读取。
- 附带事项：Homebrew 默认清理了旧安装缓存，已告知用户可重新下载；未删除项目/数据库。
- 后续：不能用宽泛 grep/sed 放行解决；改用原本有路径、输出、时间限制的内置 read_file/search。

### D07：模型补丁格式不合规

- 现象：标准 unified diff 的 hunk 数量不准，并夹带结尾 `*** End Patch`；git apply --check 拒绝。
- 复现：原补丁只读检查失败；去除仅位于结尾的独立 trailer 并 recount 后成功。
- 修复：只规范化该独立尾标记，git apply/check 同时使用 --recount；不启用 --unsafe-paths，不跳过上下文，不支持无数字的 @@。
- 验证：格式兼容通过；错误上下文与路径逃逸仍拒绝。独立只读审查无新增发现。

### D08：外部验收通过但新增测试失败

对象：task c01fba3f-14a9-4d49-9332-3a42fc131db4。最终超出 900 秒持久时限，失败；人工独立复测外部 v1 为 19/19，通过，但仓库相关测试 12 passed、5 failed：

### D09：审批、探索与重试消耗预算

- 现象：反复读文件、格式重试、grep/sed 审批；等待审批也计入 900 秒，最终任务超时。
- 下一轮仍请求与任务无关的 `ps -p 1 -o comm=`，停在审批；用户要求新一轮修复后取消旧任务，保留历史。
- 优化：优先内置工具；未精确授权的 cat/head/tail/sed/grep/rg 返回 DENIED 和替代建议，既不执行，也不进入不必要的审批暂停。显式授权的精确 argv 与其他命令原审批规则不变。
- 重试指导：小块标准 diff；失败先读当前上下文；不重复原失败补丁；修改后只运行宿主精确 test_command；不探索无关环境。
- 安全：40 步、900 秒、重复调用熔断、路径隔离、禁止 shell/网络/破坏命令均不放宽。
- 回归：新增策略与验收测试先出现 8 个预期失败，修复后目标集合 26 passed。提示词的效果还须由真实运行衡量，不能仅凭文字断言有效。

## 七、补强验收后的追加发现

### D10：大文件 EOF 返回了文件后半段，显式 null 被当默认

- 独立复现：20000 字节文本，offset=20000、20001、10**40，均错误返回 11808 字节；limit=None 错误成功。
- 原因：先读取 8192 字节文件头后，offset 超过 EOF 的分支清空缓存但没有定位至 EOF，后续继续从文件头之后读取。limit 用 get(...)=None 同时表示缺省和显式 null。
- 验收：保留 v2，再新增 v3 的 large-file-eof、large-file-past-eof、large-file-huge-offset、offset/limit null；共 32 项。旧候选触发前三项及 invalid-limit-None，先失败再修复。
- v3 SHA-256：`a87daa2b32a16b58748bf2dfe782c2e815d2d696df85d1d354ac5fc84bca3675`。

- 回归发现直接调用 HTTPRuntime 绕过 prepare_context 时仍会发出超预算请求，测试原本得到连接错误而非预算拒绝。新增实际发送前检查后，直接调用也在网络请求前失败。
- 只解析供应商 usage 的非负整数字段，将真实 input/output 与估算分开；缺失记 null，不记录正文、凭据或任意扩展字段。生产主任务将 model.usage 持久化，集成测试覆盖审批恢复后的追加和累计；无法解析响应或网络中断后的计费仍可能未知。
- 独立审查发现对所有 OpenAI 兼容配置默认注入 max_tokens 会破坏部分模型原有配置。新增红绿回归后保留未启用预算的旧请求行为，显式 max_completion_tokens 不被替换；不兼容/冲突预算在配置阶段拒绝。
